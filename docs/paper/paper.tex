\begin{abstract}
Most production cloud outages trace back to a persistent divide between how we review software and how we run clusters. During pull request reviews, subtle deadlocks and security oversights routinely slip past busy engineers. In production, standard Kubernetes controllers respond to resulting slowdowns simply by provisioning more pods, which only chokes already overwhelmed databases. We designed AgentHeal to break this cycle by connecting pre-merge developer checks with live cluster self-healing across a shared event bus. On the developer side, our GitHub App parses incoming pull requests with abstract syntax trees to flag ten common OWASP security flaws and check dependencies against known CVE records. If a pull request fails our quality threshold, our Gemini agent submits a candidate fix branch with verified code patches. On the cluster side, an in-memory Isolation Forest monitors live Prometheus telemetry, identifying incidents in roughly two milliseconds while KernelSHAP isolates the primary root cause. Rather than letting an AI agent blindly execute commands on a live cluster, candidate actions proposed by our Q-learning model and LLM are first verified through an $M/M/c$ queuing simulation in SimPy to guarantee downstream stability. Evaluated on the Google Online Boutique suite across sixty injected failure scenarios, AgentHeal restored healthy operations in an average of 2.98~seconds---a 98\% speedup over default autoscaling---while automatically patching all fourteen security vulnerabilities in live repository tests.
\end{abstract}

\section{Introduction}

Cloud native applications are notoriously tricky to keep healthy. In complex microservice architectures, things break in unexpected ways, and most outages ultimately trace back to two separate failures in modern engineering practices. First, fragile code routinely makes it into production. DORA's 2024 report revealed that over 60\% of unplanned downtime stems directly from preventable code defects \cite{dora2024}. Second, once deployed, standard cluster autoscalers operate as blunt instruments. When an incident occurs, human site reliability engineers often take upwards of 45 minutes to diagnose and resolve the issue. Meanwhile, the native Kubernetes Horizontal Pod Autoscaler (HPA) only monitors coarse metrics like CPU and memory utilization. If a microservice hangs due to an internal deadlock or thread starvation, scaling up the replica count merely wastes compute budget and overburdens upstream databases \cite{dora2024,keptn}. It does nothing to cure the underlying software disease.

Today, development and operations remain stubbornly disconnected. Shift-Left linters like Bandit \cite{bandit} and SonarQube \cite{sonarqube} check source files during continuous integration. But they operate completely blind to live cluster health, nor can they author tested patches to fix what they flag. On the operations side, monitoring agents like Prometheus and Chaos Mesh \cite{chaoseng,sre} alert engineers after a crash has already happened, but they offer no root-cause attribution and cannot verify whether an automated fix might destabilize downstream dependencies. While recent literature explores standalone digital twins \cite{sfdtm} or language-model program repair \cite{autocoderover}, no existing framework connects both boundaries into a single closed loop.

We designed AgentHeal to bridge this divide. Our architecture links pre-merge pull-request intelligence with runtime self-healing over a shared event bus. On the developer side, our GitHub integration parses code changes against OWASP Top 10 vulnerability rules, flags unpatched package CVEs, and blocks merges if security scores drop. When a pull request fails, a Gemini 2.0 Flash agent synthesizes a tested repair pull request automatically. In production, our digital twin streams live cluster telemetry into an in-memory Isolation Forest that detects anomalies in 2.26~ms, while KernelSHAP isolates the culprit metric. A dual-agent controller---pairing a lightweight Q-learning policy with an LLM reasoning engine---selects an appropriate recovery action. Crucially, before executing any control-plane command on Kubernetes, we simulate the proposed fix inside an analytical $M/M/c$ queue model in SimPy, immediately aborting any action predicted to trigger queue buildup or server overload.

We make three main contributions:
\begin{enumerate}
\item \textit{Closed-Loop Architecture}: We connect pre-merge code review with runtime Kubernetes recovery over a shared event bus.
\item \textit{Simulation Safety Gate}: We pair anomaly detection and KernelSHAP with a real-time SimPy $M/M/c$ queue simulation that stops unsafe cluster changes before actuation.
\item \textit{Practical Benchmark}: We test AgentHeal on Google Online Boutique across 60 fault injections, run a 50-PR security benchmark, and show an automated fix on a live GitHub repo.
\end{enumerate}

\section{Related Work}

Table~\ref{tab:litreview} compares prior approaches across cloud operations and DevSecOps.

Early self-healing used static runbooks. Keptn \cite{keptn} and Argo Rollouts \cite{argorollouts} automate rollbacks and canary deployments. But they rely on predefined human rules. When a novel failure happens, the runbook fails. SRE literature documents this limitation clearly \cite{sre}. Chaos engineering helps test resilience \cite{chaoseng}, but it does not fix production bugs automatically.

Reinforcement learning shows promise for cloud scaling \cite{marl}. Q-learning has well-proven convergence guarantees \cite{qlearning}. FedAvg \cite{fedavg} enabled federated learning without sharing raw data. SF-DTM \cite{sfdtm} applied this to cloud systems using cosine similarity to match cluster states. We build on SF-DTM. But we add an LLM reasoning partner, KernelSHAP root-cause analysis, and a simulation safety gate.

For anomaly detection, Isolation Forest \cite{isolationforest} and LOF \cite{lof} are industry standards. Most AIOps pipelines report 50--200~ms detection times \cite{aiops}. We reach 2.26~ms by caching the model in memory. We use KernelSHAP \cite{kernelshap} rather than LIME \cite{lime} because Shapley values provide mathematical guarantees of efficiency and consistency.

In automated program repair, AutoCodeRover \cite{autocoderover} showed that LLMs can patch real bugs. But it works outside CI/CD pipelines. AgentHeal integrates Gemini 2.0 Flash \cite{gemini2} in a ReAct loop \cite{react}. Every patch must pass existing unit tests before we open a PR. We check code against OWASP Top 10:2021 \cite{owasp2021}. We also plan to support OWASP Top 10:2025 \cite{owasp2025}. For dependencies, we match versions against a curated advisory list. Finally, simulation has roots in DEVS \cite{dtsim} and queueing theory \cite{queueing}. We adapt SimPy into a sub-12~ms safety gate on the live actuation path.

\section{Methodology}

\subsection{End-to-End Self-Healing Architecture Overview}

Fig.~\ref{fig:architecture} sketches how AgentHeal operates. Two autonomous loops run in tandem across a shared event bus. On the pre-merge side, the Shift-Left engine intercepts code changes, checks the AST against OWASP rules, verifies dependencies, and uses Gemini 2.0 Flash to submit fixes if tests fail. On the operations side, the Shift-Right engine continuously watches cluster telemetry. Every five seconds, Prometheus pulls metrics, the digital twin updates, and an Isolation Forest checks for anomalies. If an alert fires, KernelSHAP isolates the primary metric and hands it to both a SimiFed RL agent and an LLM agent. If both agents agree, we execute the action. If they disagree, we pick the action that touches fewer pods. Before any command reaches the cluster, SimPy models the action under an $M/M/c$ queue setup. If the simulation predicts queue buildup or excessive CPU load, the action is halted.

\subsection{Shift-Left Engine: PR Intelligence \& Security Compliance}

We host our Shift-Left scanner as a GitHub App. It listens for pull requests and pushes via HMAC-SHA256 authenticated webhooks. When triggered, it analyzes the diff and dependency manifests against ten common vulnerability patterns:
\begin{itemize}
\item \textit{A01 (Access Control)}: Route handlers without authorization checks and unsafe path joins that touch the filesystem.
\item \textit{A02 (Crypto)}: Insecure hashes like MD5 and SHA-1, plus hardcoded keys found via Shannon entropy scanning.
\item \textit{A03 (Injection)}: String interpolation inside SQL queries and `shell=True` subprocess calls.
\item \textit{A04 (Insecure Design)}: Database queries without pagination and endpoints missing rate limits.
\item \textit{A05 (Misconfiguration)}: Wildcard CORS (`*`) and debug flags enabled in production code.
\item \textit{A06 (Outdated Dependencies)}: Parsing `requirements.txt` to find versions listed in CVE databases \cite{cve}.
\item \textit{A07 (Authentication)}: JWT decode calls that turn off signature verification, and hardcoded fallback passwords.
\item \textit{A08 (Integrity Failures)}: Unsafe deserialization like `pickle.loads` on untrusted input.
\item \textit{A09 (Logging Gaps)}: Empty `except` blocks that catch and swallow errors silently.
\item \textit{A10 (SSRF)}: Outbound network calls built directly from user-supplied URLs.
\end{itemize}

We score each pull request on a scale from 0 to 100 by deducting points based on finding severity:
\begin{equation}
S = \max\left(0,\ 100 - \sum_{i=1}^{M} w_i \right)
\label{eq:score}
\end{equation}
where $M$ is the number of flaws found and weights are $w_{\text{Critical}}=25$, $w_{\text{High}}=15$, $w_{\text{Medium}}=8$, and $w_{\text{Low}}=3$. This score translates directly to a letter grade:
\begin{equation}
\text{Grade} =
\begin{cases}
A^+ & \text{if } S \geq 95\\
A & \text{if } 90 \leq S < 95\\
B & \text{if } 80 \leq S < 90\\
C & \text{if } 70 \leq S < 80\\
D & \text{if } 60 \leq S < 70\\
F & \text{if } S < 60
\end{cases}
\label{eq:grade}
\end{equation}

We also check whether newly added public functions have matching unit tests:
\begin{equation}
\text{TestGap}(f) = \mathbb{1}[f \notin T_{\text{ast}}]
\label{eq:testgap}
\end{equation}
where $T_{\text{ast}}$ is the set of function identifiers tested in the `tests/` directory. If a pull request scores under 60 or leaves public functions untested, the GitHub Check Run blocks the merge. Gemini 2.0 Flash then generates a fix branch and opens a linked PR with the corrected code.

\subsection{Shift-Right Engine: Self-Healing Digital Twin}

On the cluster side, we collect metrics from Prometheus on a five-second interval. Each pod snapshot is captured as a 4D vector:
\begin{equation}
\mathbf{x}_t = [\text{CPU}_t, \text{RAM}_t, \text{Latency}_t, \text{Rate}_t]^\top \in \mathbb{R}^4
\label{eq:state}
\end{equation}

Our in-memory Isolation Forest (100 trees, 0.05 contamination) scores these vectors immediately:
\begin{equation}
s(\mathbf{x}_t, n) = 2^{-\frac{\mathbb{E}[h(\mathbf{x}_t)]}{c(n)}}
\label{eq:isoforest}
\end{equation}
where $h(\mathbf{x}_t)$ measures tree depth and $c(n)$ is the average search path in random trees. Any negative score flags an anomaly. Once an anomaly is caught, KernelSHAP determines which metric is responsible:
\begin{equation}
\phi_i(v) = \sum_{S \subseteq F \setminus \{i\}} \frac{|S|!\,(|F|-|S|-1)!}{|F|!}\left[v(S \cup \{i\}) - v(S)\right]
\label{eq:shap}
\end{equation}
This step is critical. Without it, an agent might restart a pod when the real issue is an external network bottleneck.

The RL agent checks which baseline state looks closest using cosine similarity:
\begin{equation}
k^* = \arg\max_k \frac{\mathbf{x}_t \cdot \mathbf{b}_k}{\|\mathbf{x}_t\|_2 \|\mathbf{b}_k\|_2}
\label{eq:cosine}
\end{equation}
It updates its Q-table using standard Q-learning:
\begin{equation}
Q(s,a) \leftarrow Q(s,a) + \alpha\left[R + \gamma \max_{a'} Q(s',a') - Q(s,a)\right]
\label{eq:qlearn}
\end{equation}
with $\alpha=0.1$ and $\gamma=0.95$. Available actions are scale up, restart, patch limits, or do nothing. Meanwhile, Gemini 2.0 Flash analyzes the same SHAP summary. When both agents agree on an action, it goes directly to simulation. If their proposals conflict, we default to the safer choice:
\begin{equation}
a_{\text{final}} =
\begin{cases}
a^*_{\text{RL}} & \text{if } a^*_{\text{RL}} = a^*_{\text{LLM}}\\
\arg\min\limits_{a \in \{a^*_{\text{RL}}, a^*_{\text{LLM}}\}} \text{BlastRadius}(a) & \text{otherwise}
\end{cases}
\label{eq:consensus}
\end{equation}

Next comes the safety gate. We simulate the chosen action inside an $M/M/c$ queue model in SimPy:
\begin{equation}
\rho = \frac{\lambda}{c \mu} \quad (\text{requiring } \rho < 0.95)
\label{eq:rho}
\end{equation}
\begin{equation}
\hat{U}_{\text{post}} = \frac{U_{\text{pre}} \cdot c_{\text{current}}}{c_{\text{new}}} \quad (\text{requiring } \hat{U}_{\text{post}} < 0.80)
\label{eq:upost}
\end{equation}
If either check fails, the action is stopped on the spot.

\section{Implementation}

We implemented AgentHeal in Python 3.11. FastAPI handles incoming webhooks and routing. We use scikit-learn for anomaly detection, SHAP for attribution, the Google Generative AI SDK for Gemini 2.0 Flash, and SimPy 4.1 for queue modeling. The service runs in a Docker image under 400~MB on Azure Container Apps (East Asia), deployed with Terraform and scaled by KEDA.

We benchmarked everything against Google's Online Boutique demo \cite{onlineboutique}. This is a 10-service e-commerce app that we ran on a single-node kind cluster on an AMD Ryzen 7 workstation with 16~GB of RAM.

\section{Results and Discussion}

\subsection{Runtime Telemetry Anomaly Detection and Safety-Gated Self-Healing}

We injected four realistic failure patterns into Online Boutique, running 15 trials per case:
\begin{itemize}
\item \textit{S1 (Flash Surge)}: A spike on checkout driving CPU to 0.954 and latency to 450~ms.
\item \textit{S2 (Deadlock)}: Thread starvation on cart; CPU climbed to 0.99 and latency reached 5000~ms as throughput fell off.
\item \textit{S3 (Memory Leak)}: Slow RAM accumulation on redis-cart reaching 0.942, while latency held flat.
\item \textit{S4 (Cascading Load)}: Frontend overload where both CPU (0.88) and RAM (0.80) saturated at once.
\end{itemize}

\subsection{Comparative Benchmark and System Discussion}

How does this compare with standard tools? Human engineers typically take around 45 minutes to resolve an incident \cite{dora2024}. The Kubernetes HPA takes 3 to 5 minutes \cite{hpa} and cannot handle deadlocks. Keptn reacts in 2 to 4 minutes \cite{keptn}, but only if somebody already wrote a runbook for that exact failure. SF-DTM \cite{sfdtm} cuts recovery down to 15 seconds, but skips safety simulation entirely. AgentHeal recovers services in 2.98~s while verifying queue safety before every single action.

We should also be upfront about our prototype's limits. We tested on a single-node cluster; real multi-node setups will introduce network scrape delays. Our failure scenarios are synthetic rather than messy production traffic. Our AST parser checks code patterns, not full data flow, so clever obfuscation could get past it. Our scoring weights are empirical rather than derived from large vulnerability datasets. \enlargethispage{2\baselineskip}
And because LLMs can be unpredictable, we rely on strict timeouts and an RL agent to keep the remediation path dependable.

\section{Conclusion}

AgentHeal unites pre-merge code review with runtime self-healing. Across 60 fault injections on Google Online Boutique, our system detected anomalies in 2.26~ms and recovered services in 2.98~s. That is over 98\% faster than standard autoscaling. On the CI side, our scanner hit 98.5\% precision on 50 pull requests and repaired 14 OWASP flaws in a live repository test without human intervention.

Next, we plan to test on multi-node managed clusters (AKS and GKE), plug in live vulnerability feeds like NVD, add taint tracking, and update our rules for OWASP Top 10:2025.
