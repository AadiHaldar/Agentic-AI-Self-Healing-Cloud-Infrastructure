\begin{abstract}
Indeed, the typical microservice in modern cloud infrastructures is vulnerable to unexpected downtime. The default Kubernetes autoscaler in case of deadlock will start spinning up new pods. It would hardly help and would result in even faster collapse of the database. Our experiments showed that poorly-written code could get easily unnoticed during routine pull request reviews. To solve this problem, we developed AgentHeal. What we have done here is creating an integrated loop where pre-merge code review is directly linked to self-healing of the live cluster. Upon opening a pull request, our GitHub bot analyses the code for ten OWASP security flaws and for presence of CVEs in all third-party libraries. If the score falls below our safety bar, the merge is stopped immediately. Then, an agent based on Gemini 2.0 Flash creates the branch with fixed code, passing all unit tests. In the live cluster, an Isolation Forest in-memory model monitors Prometheus metrics. In our experiments, it detected anomalies in less than two milliseconds. With the help of KernelSHAP, we find out what was causing the anomaly. Two agents---the Q-learning policy and the LLM---choose the optimal fix. Nothing gets into the cluster untested. We run our proposed action through the simulated test with SimPy $M/M/c$ queue. If our queue is going to be overloaded, we do not implement the action. This is how we protect our cluster. The average recovery time of our system in 60 failed runs on Google Online Boutique was 2.98~seconds. Compared to default Kubernetes autoscaling, it reduced recovery time by 98\%. In addition, on the real-life GitHub repository, our system has patched all fourteen vulnerabilities without human intervention.
\end{abstract}

\section{Introduction}

Indeed, maintaining reliable operations of microservices in cloud infrastructures is still a challenging engineering problem. As a result, unplanned outages occur regularly as deployments get more distributed. Most often, two interrelated issues are at the core of the problem. First, flawed code finds its way into production branches. Based on DORA's 2024 survey, over 60\% of unplanned outages in cloud environments are caused by preventable software bugs \cite{dora2024}. Second, existing cluster controllers fail to react adequately to stalled services. Once an issue arises, engineers spend on average 45 minutes manually diagnosing logs \cite{dora2024}. At the same time, the default Horizontal Pod Autoscaler in Kubernetes considers only coarse CPU and memory metrics \cite{hpa}. If a pod locks up, spawning more replicas will not solve the issue but will increase load on downstream databases and cause the whole cluster to fail faster \cite{keptn}. The root cause is left completely unresolved.

Currently, there are two completely independent processes---development and live cluster operations. While static linters such as Bandit \cite{bandit} and SonarQube \cite{sonarqube} analyze pull requests in the CI pipeline, they know nothing about cluster health and cannot generate a valid fix patch. Meanwhile, while monitoring tools such as Prometheus and Chaos Mesh \cite{chaoseng,sre} notify operators of an outage, they do not provide any automated root cause identification. Current automation tools run recovery commands in the live environment without checking the action for possible cascade failures among other dependent microservices. Although there have been attempts to use digital twins for cluster state matching \cite{sfdtm} or language models for program repair \cite{autocoderover}, there is currently no platform that connects pre-merge security checks with live cluster self-healing in a single closed loop.

To fill this gap, we created AgentHeal. What we have done here is establishing a direct connection between the auditing of pull requests and Kubernetes self-healing through a shared event bus. On the development side, our GitHub bot audits incoming pull requests for vulnerabilities in ten OWASP classes and searches for dependencies associated with a known CVE record. In case a pull request fails our safety check, the merge is instantly prevented, and an agent based on Gemini 2.0 Flash \cite{gemini2} creates a fix branch that passes all tests. On the runtime side, an in-memory Isolation Forest \cite{isolationforest} analyzes Prometheus metrics every five seconds in 2.26~ms. Using KernelSHAP \cite{kernelshap}, the system detects the responsible metric. After that, a Q-learning policy and an LLM agent select candidate remediation actions. No command is run in the cluster until it passes validation. Each proposed action is evaluated through an $M/M/c$ queue simulation in SimPy \cite{queueing}. If our queue is projected to be overloaded, the action is rejected immediately. This is how we protect our cluster.

We make three primary contributions:
\begin{enumerate}
\item \textit{Closed-Loop Architecture}: We design and implement an end-to-end framework linking pre-merge pull request security checks with runtime Kubernetes remediation via a shared event bus.
\item \textit{Simulation-Gated Remediation}: We introduce a pre-actuation safety gate that evaluates candidate self-healing actions through an $M/M/c$ queue simulation in SimPy, preventing cascading cluster collapse.
\item \textit{Empirical Evaluation}: We evaluate AgentHeal on Google Online Boutique across 60 fault injections, benchmark 50 synthetic pull requests, and demonstrate fully automated vulnerability remediation on a live GitHub repository.
\end{enumerate}

\section{Related Work}

Table~\ref{tab:litreview} summarizes the previous works related to autonomous cloud operations and DevSecOps.

Previous self-healing cloud platforms have mainly utilized automation scripts. Canaries and basic rollbacks are automated in Keptn \cite{keptn} and Argo Rollouts \cite{argorollouts} based on certain policies; however, none of the systems is capable of diagnosing new failure cases and resolving the deadlock situations which need a code fix. The conventional reliability engineering approach like SRE error budgets \cite{sre} and Chaos Engineering \cite{chaoseng} provides diagnostics but needs human intervention to solve the problem. Traditional delivery pipelines \cite{humblefarley,fowlerbg} focus on deployment throughput and not on runtime defect mitigation.

Reinforcement learning can be used as an alternative approach for cloud resource management \cite{marl}. Tabular Q-learning \cite{qlearning} converges for sure but suffers from state space explosion problem without discretization. Federated learning solutions such as FedAvg \cite{fedavg} allow coordinating decentralized learning, although still focusing on offline batch learning. In cloud operation, SF-DTM \cite{sfdtm} has used digital twin cosine similarity matching in order to speed up cluster recovery; nevertheless, it does not check safety before executing any cluster commands.

As regards telemetry anomaly detection, Isolation Forest \cite{isolationforest} and Local Outlier Factor \cite{lof} are still widely used. Usually, typical industry AIOps solutions report detection delays between 50 and 200~ms \cite{aiops}. In our solution, using a cached version of the Isolation Forest model in memory lowers the delay time down to 2.26~ms. KernelSHAP \cite{kernelshap} is selected against the linear surrogates like LIME \cite{lime} because the Shapley value has the property of mathematical consistency when evaluating repeatedly.

In automated program repair, AutoCodeRover \cite{autocoderover} has shown that large language models could fix the defects in real-world code, although it is an offline process outside CI/CD pipelines. AgentHeal uses Gemini 2.0 Flash \cite{gemini2} in the active ReAct cycle \cite{react} which means that all generated patches have to pass unit tests first before the code change by pull request. Our code change assessment is based on OWASP Top 10:2021 criteria \cite{owasp2021}, but will be extended later to OWASP Top 10:2025 \cite{owasp2025}. Finally, discrete event simulation has a rich history in DEVS \cite{dtsim} and queueing theory \cite{queueing}. SimPy is adopted to use as a sub-12~ms validation gate directly on the live actuation path.

\section{Methodology}

\subsection{End-to-End Self-Healing Architecture Overview}

Fig.~\ref{fig:architecture} shows the general architecture of the AgentHeal platform. The platform controls two independent feedback loops through a shared event bus. On the one hand, there is the development cycle in which the pre-merge engine analyzes pull requests for security flaws through abstract syntax tree examination, dependency manifest checking, and Gemini 2.0 Flash patch generation based on test verification. On the other hand, there is the cluster runtime during which the runtime engine ensures cluster health. Metrics collection occurs every five seconds with Prometheus, while an in-memory Isolation Forest scores incoming vectors in real-time. Upon the appearance of an alert, KernelSHAP determines the main cause of the issue. After that, the problem diagnosis is given to both Q-learning agent and LLM supervisor. In case of agreement of the agents concerning a solution, the action is simulated. In case of disagreement, the action with the smallest blast radius is chosen. All actions are tested before being launched inside the cluster. Any interaction with the cluster goes through a SimPy $M/M/c$ queue model estimation of cluster stability. If there is predicted to be a risk of queue growth or increased drop rates, the action is rejected.

\subsection{Shift-Left Engine: PR Intelligence \& Security Compliance}

We implemented our pre-merge scanner as a GitHub App. It receives pull request and push events through HMAC-SHA256 authenticated webhooks. Upon receiving a payload, it parses incoming diffs and dependency manifests against ten vulnerability classes:
\begin{itemize}
\item \textit{A01 (Access Control)}: Route handlers without authorization checks and unsafe path joins that touch the filesystem.
\item \textit{A02 (Crypto)}: Insecure hashes like MD5 and SHA-1, plus hardcoded keys found via Shannon entropy scanning.
\item \textit{A03 (Injection)}: String interpolation inside SQL queries and `shell=True` subprocess calls.
\item \textit{A04 (Insecure Design)}: Database queries without pagination and endpoints missing rate limits.
\item \textit{A05 (Misconfiguration)}: Wildcard CORS (`*`) and debug flags enabled in production code.
\item \textit{A06 (Outdated Dependencies)}: Parsing `requirements.txt` to find versions listed in CVE databases \cite{cve}.
\item \textit{A07 (Authentication)}: JWT decode calls that turn off signature verification, and hardcoded fallback passwords.
\item \textit{A08 (Integrity Failures)}: Unsafe deserialization like `pickle.loads` on untrusted input.
\item \textit{A09 (Logging Gaps)}: Empty `except` blocks that catch and swallow errors silently.
\item \textit{A10 (SSRF)}: Outbound network calls built directly from user-supplied URLs.
\end{itemize}

We score each submission on a 100-point scale. Points are subtracted based on the severity of each identified issue:
\begin{equation}
S = \max\left(0,\ 100 - \sum_{i=1}^{M} w_i \right)
\label{eq:score}
\end{equation}
Here, $M$ represents the total count of detected flaws. Severity penalties are set to $w_{\text{Critical}}=25$, $w_{\text{High}}=15$, $w_{\text{Medium}}=8$, and $w_{\text{Low}}=3$. We convert this numerical score directly into an academic letter grade:
\begin{equation}
\text{Grade} =
\begin{cases}
A^+ & \text{if } S \geq 95\\
A & \text{if } 90 \leq S < 95\\
B & \text{if } 80 \leq S < 90\\
C & \text{if } 70 \leq S < 80\\
D & \text{if } 60 \leq S < 70\\
F & \text{if } S < 60
\end{cases}
\label{eq:grade}
\end{equation}

We also verify test coverage on newly added public functions:
\begin{equation}
\text{TestGap}(f) = \mathbb{1}[f \notin T_{\text{ast}}]
\label{eq:testgap}
\end{equation}
where $T_{\text{ast}}$ contains all function names covered by test cases in \texttt{tests/}. If a pull request scores below 60 (Grade F) or contains critical flaws, the GitHub App sets the commit check status to \texttt{action\_required}, blocking the merge. When this occurs, our Gemini 2.0 Flash agent creates a remediation branch. It authors code fixes and verifies that all unit tests pass before opening a remediated pull request.

\subsection{Shift-Right Engine: Self-Healing Digital Twin}

In the live cluster, the digital twin collects Prometheus metrics every five seconds. A four-dimensional vector corresponds to each pod health status:
\begin{equation}
\mathbf{x}_t = [\text{CPU}_t, \text{RAM}_t, \text{Latency}_t, \text{Rate}_t]^\top \in \mathbb{R}^4
\label{eq:state}
\end{equation}

The in-memory Isolation Forest (100 trees, 0.05 contamination) evaluates the vector in real-time:
\begin{equation}
s(\mathbf{x}_t, n) = 2^{-\frac{\mathbb{E}[h(\mathbf{x}_t)]}{c(n)}}
\label{eq:isoforest}
\end{equation}
where $h(\mathbf{x}_t)$ is the observed path length and $c(n)$ is the average path length of unsuccessful searches, with negative values generating an alert. KernelSHAP attributes the problem to certain resource dimensions:
\begin{equation}
\phi_i(v) = \sum_{S \subseteq F \setminus \{i\}} \frac{|S|!\,(|F|-|S|-1)!}{|F|!}\left[v(S \cup \{i\}) - v(S)\right]
\label{eq:shap}
\end{equation}
Such a process is needed to avoid container restarts if an external network dependency represents the problem cause.

The reinforcement learning agent finds the closest baseline state using cosine similarity:
\begin{equation}
k^* = \arg\max_k \frac{\mathbf{x}_t \cdot \mathbf{b}_k}{\|\mathbf{x}_t\|_2 \|\mathbf{b}_k\|_2}
\label{eq:cosine}
\end{equation}
and updates its Q-table using the temporal difference learning approach:
\begin{equation}
Q(s,a) \leftarrow Q(s,a) + \alpha\left[R + \gamma \max_{a'} Q(s',a') - Q(s,a)\right]
\label{eq:qlearn}
\end{equation}
with learning rate $\alpha=0.1$ and discount factor $\gamma=0.95$. Available actions include pod restarts, replica scaling, memory limit adjustments, or no-op monitoring. At the same time, Gemini 2.0 Flash evaluates the SHAP summary. If both agents come up with the same action, it goes to simulation. When they disagree, the action with lower blast radius is selected.

There is no action executed without simulation beforehand. Candidate actions are evaluated using the SimPy $M/M/c$ queue model \cite{queueing}:
\begin{equation}
P_0 = \left[ \sum_{k=0}^{c-1} \frac{(c\rho)^k}{k!} + \frac{(c\rho)^c}{c!(1-\rho)} \right]^{-1}, \quad \rho = \frac{\lambda}{c\mu} < 1
\label{eq:mmc}
\end{equation}
which estimates queue length $L_q$, server utilization rate $\rho$, and drop rate for the next sixty seconds. If there is predicted to be a risk of more than 95\% utilization ($\rho \geq 0.95$) or more than 5\% request drops, the action is rejected, and the system switches to safe horizontal pod scaling.

\section{Implementation}

AgentHeal was developed using Python 3.11. The implementation uses FastAPI for asynchronous webhook parsing and telemetry delivery. The runtime depends on scikit-learn to execute the Isolation Forest model, SHAP to perform Shapley analysis, the Generative AI SDK by Google to communicate with Gemini 2.0 Flash \cite{gemini2}, and SimPy 4.1 for queue simulation. Everything is bundled into a Docker image, weighing less than 400~MB. The live system runs on Azure Container Apps in the East Asia region. It is provisioned using Terraform and auto-scaled using KEDA. To evaluate the runtime, we used Google's Online Boutique benchmark \cite{onlineboutique} that consists of ten interconnected microservices in a single-node Kubernetes \texttt{kind} cluster running on an AMD Ryzen 7 5700X workstation with 16~GB of DDR4 memory.

\subsection{Comparative Benchmark and System Discussion}

How does AgentHeal compare to other solutions? It takes about 45 minutes on average to heal the services through human on-call triage \cite{dora2024}. The default Kubernetes autoscaler takes from 3 to 5 minutes to stabilize pods \cite{hpa}, but it cannot resolve deadlocks. Rule-based systems such as Keptn \cite{keptn} require 2 to 4 minutes to recover, but completely rely on manual scripts. Although SF-DTM \cite{sfdtm} takes only about 15 seconds to recover, it does not have any simulation safety checks before actuation. AgentHeal provides a mean recovery time of 2.98~seconds with the verification of queue safety beforehand.

There are some shortcomings to our prototype. First, testing was done on a local \texttt{kind} cluster; multi-node clouds would introduce network scrape delays. Second, failure cases were generated via synthetic fault injection rather than production traffic. Third, our static auditor uses syntax pattern evaluation rather than whole-program taint tracking. Finally, as language models may vary in latency, Q-learning-based arbitration is needed for our dual-agent recovery method. \enlargethispage{2\baselineskip}

\section{Conclusion}

AgentHeal merges pre-merge code review with runtime self-healing. Across sixty fault injections on Google Online Boutique, the system detects anomalies within 2.26~ms and recovers cluster stability within 2.98~seconds. This represents a 98\% speedup over standard autoscaling. On the developer side, our scanner achieved 98.5\% precision on 50 pull requests and autonomously patched all fourteen security flaws on a live GitHub repository.

In future work, we plan to evaluate multi-region managed clusters (AKS and GKE), integrate live CVE streams like OSV and NVD, incorporate dynamic taint analysis, and expand rules for modern web threats.
